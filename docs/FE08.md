# FE08 — Checkpoint 1: error states, empty states, and edge cases

Live primary flow: https://leaddesk-capstone.vercel.app/discovery

## Failure inventory and recovery

| Case | Deliberate behavior | Sabotage / verification |
| --- | --- | --- |
| First run | Two click-to-fill examples and project guidance; Send disabled until useful input | Empty browser conversation, select an example |
| Empty / whitespace input | Send disabled; submit handler also rejects blank input | Spaces and empty form |
| Network failure before response | Connection guidance; visitor message stays; retry only last response | Browser fetch rejects before send |
| Connection killed mid-stream | Partial text and earlier turns remain; designed error, retry only last response | Controlled stream errors after its first text delta |
| Provider / API failure | Safe 503 or stream-error message; no provider details exposed | Unit test throws inside server generation; UI network tests inject failures |
| Rate limit | Wait-one-minute guidance; no automatic retry loop; server Retry-After: 60 | Inject 429, then clear failure and retry |
| Slow response | Reply-shaped skeleton; after 8 seconds an explanatory delay notice; Stop always available | Hold stream open; stop without treating cancellation as an error |
| Empty model output / no results | Explicit no-usable-response prompt with Retry and suggestion to add detail | Finish an empty AI SDK stream |
| Incomplete tool call | Finished/stopped streams show a designed tool error rather than an endless loading label | Component test with partial tool input |
| Malformed tool output | Zod validation contains bad data in an alert; no score is invented | Browser stream returns invalid tool result |
| Route render failure | error.tsx with Next retry (re-fetch/re-render), without exposing thrown details | Component test invokes retry callback |
| Double retry / send while pending | Synchronous guard plus SDK pending state prevents duplicate requests | Two retry clicks in one event turn; assert single network request |
| Long input / long conversation | 2,000-character composer limit with count; conversation limit explains how to restart; API caps body size | Existing API guards, composer attributes, conversation guard |
| Refusal | Plain text response remains readable; visitor can rephrase or restart | Text renderer treats output as text, never executable HTML |

## Mobile choices

The conversation scroll area is separate from the page, with overscroll containment. The composer stays in normal layout rather than being pinned over the keyboard. Dynamic/small viewport units, safe-area padding, 16px mobile text input (avoiding focus zoom), and 44px controls address common Safari issues. Browser automation includes iPhone 13 mobile WebKit. This is engine/device emulation, not a physical iPhone; physical-device keyboard and rubber-band behavior have not been verified.

## Test method and evidence

Failure injection lives only in tests. There are no production sabotage query parameters, mock provider modes, or secret exposure. tests/chat-route.test.ts throws a provider exception through the actual POST handler. e2e/edges.spec.ts drives the real chat component and AI SDK parser with controlled fetch/stream failures. It checks network-before-send, killed mid-stream, 429, empty output, malformed tool output, slow response/stop, retry duplication, first run, and a typed success card. Both Chromium and mobile WebKit run the edge suite. Happy-path tests fail on console errors or uncaught browser errors.
