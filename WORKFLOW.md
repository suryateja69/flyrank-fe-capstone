# AI-assisted workflow drill

I built a device-local notification preferences form for LeadDesk twice, starting both independent AI sessions from commit `3b9dd18`. The branches are `workflow-vague` and `workflow-precise`. Neither session inspected the other output. Exact instructions and observed timings are recorded in `docs/workflow/round-one.md` and `docs/workflow/round-two.md`. Both versions are practice preference editors; neither sends notifications.

The vague prompt was “Add a notification preferences form to LeadDesk.” Its first output was accepted unchanged. In `src/components/notification-preferences-form.tsx`, it invented three categories: new leads, status updates, and weekly summary. It provided labelled native checkboxes, a fieldset, explicit Save, a status message, and storage failure feedback. These are useful results from an underspecified prompt, but the product decisions were implicit. Existing tests passing did not establish that the new feature worked.

The precise prompt referenced the settings page, existing form, test setup, and project rules. Exploration preceded a written plan, implementation, and verification. It specified an email checkbox and daily/weekly digest selector, defaults, save-only persistence, failure behavior, and example reload behavior. The same component path now uses `z.strictObject` to constrain the stored shape. The select is disabled when email is off while retaining its chosen frequency. This is a concrete behavioral difference from the three independently toggled categories, illustrating how explicit requirements shape the output.

One AI mistake I caught in the vague version was accepting an entire parsed cache object with `setPreferences(stored)` after checking only three boolean properties. Extra unexpected properties survive and are written back on Save. I preserved this mistake on the vague branch so the comparison remains inspectable. The precise schema rejects unknown properties and invalid enum values rather than trusting a partially checked object.

Accessibility review found useful native controls in both versions. The precise form additionally has an accessible form name through `aria-labelledby`; both distinguish success status from error alerts and clear stale feedback on edits. Its new tests exercise keyboard interaction, disabled controls, persistence across remounts, malformed cache, blocked storage, and failed saves. Automated component tests do not constitute a screen-reader or full browser accessibility audit.

Review effort shifted from discovering unspecified behavior to checking stated examples. Round one recorded roughly eighty seconds from its first captured timestamp through verification, excluding a small unmeasured setup interval. Round two includes additional test and build work; its record gives observed timing rather than an invented productivity claim. Both production builds and typechecks were run. The vague branch retains its first output and existing tests; the precise branch adds focused regression coverage. Three concrete rules in `CLAUDE.md` carry the storage, feedback, and dependent-control lessons into later work.
